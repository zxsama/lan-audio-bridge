# 0.3.1 验证记录

本次验证覆盖 Windows 原生音量、托盘运行、VAIO 缓冲，以及桌面接收端的调度和心跳修复。日期：2026-11-07。

## Windows

- Voicemeeter Standard 1.1.3.0 / VAIO 3.4.1.9，Windows PowerShell 5.1 与 PowerShell 7。
- 两个 PowerShell 版本各通过 69 项主流程、23 项会话恢复、14 项驱动选项、34 项提权入口、25 项引擎偏好、28 项托盘偏好检查。
- 进程定时器策略的原生写入、读回和恢复另在两个版本各通过 19 项检查。
- 原生 Windows 音量开启前，100%、50%、0% 和静音不改变网络 PCM；开启后音量衰减生效，0% 和静音的采集 PCM 全部为零。
- 原生托盘启动与隐藏窗口已实际应用，VAIO 6 缓冲由 7168 降至 3072；保留内部时钟 512、原端点音量及静音状态。
- 短时隐藏窗口对照未复现原始卡顿；定时器保护属于针对已知 Windows 行为的缓解措施，不能据此断言已证明本机卡顿的唯一根因。

实际 Windows → 有线局域网 → 接收端输出监视器 → 返回观测，10 个提示音：

| 配置 | 冷启动 | 稳态中位数 | 稳态最大值 |
| --- | ---: | ---: | ---: |
| VAIO 7168 | 302.770 ms | 342.679 ms | 350.638 ms |
| VAIO 3072、托盘运行 | 240.446 ms | 241.251 ms | 253.144 ms |

该测量包含 Windows 共享播放接口、驱动、Voicemeeter、网络、接收软件、录音缓冲和返回开销，不包含实体音响的声学延迟。接收端此时仍使用上一版本和 50 / 30 / 20 缓冲，不能将结果视为新接收端完整部署后的延迟。

## 接收端

在独立 WSL Docker、null 输出中验证当前源码，153 项单元测试全部通过，无跳过。两组缓冲均通过四手机总线、12 次切换、独立停止、音量、短通知、满幅混音及接收器/播放器故障恢复。

下表按“路由 / 播放器 / 首播接收”列出缓冲。每种模式含 1 个冷启动和 29 个稳态标记：

| 缓冲 | 模式 | 冷启动 | 稳态中位数 | P95 |
| --- | --- | ---: | ---: | ---: |
| 30 / 15 / 15 ms | 桌面 | 64.069 ms | 61.870 ms | 67.959 ms |
| 30 / 15 / 15 ms | 与 DLNA 总线混音 | 94.582 ms | 94.688 ms | 98.478 ms |
| 20 / 10 / 10 ms | 桌面 | 79.839 ms | 76.760 ms | 79.969 ms |
| 20 / 10 / 10 ms | 与 DLNA 总线混音 | 110.002 ms | 112.054 ms | 115.352 ms |

两档各进行 120 秒桌面连续性检查：没有应用补零、缺包、队列丢弃、超过 0.5 ms 的近零缺口或逐样本突变。测试期间实际发生约 400–484 ms 的墙钟回调，单调时钟心跳维持了接收状态。非阻塞管道背压没有造成输出缺口，不能单凭背压次数判定卡顿。

每档仅一次延迟会话，路由建立和调度相位仍是影响因素。结果支持将 30 / 15 / 15 作为有线环境的候选配置，不证明它在所有设备上都更快。混音连续性沿用原有较粗的检查，不能升级为混音逐样本无缺口结论。

## 限制

- 软件链路尚未达到 10–20 ms 的单向播放目标。
- 120 秒稳定性不等于数小时发送端与接收端时钟漂移已经解决。
- 保留 48 kHz、双声道 PCM16 和防削顶混音余量；没有通过更高标称采样率或位深增加源信息。
- 两路都停止时仍释放播放路由并挂起输出；外部接口是否停止物理载波需设备侧确认。
- 本次代码验证与 NAS 实际部署状态分别记录，未把镜像构建或共享目录更新当成运行中应用已更新。
