# 延迟验证

本页给出当前实现的实测结论、延迟构成和测量方法。按时间记录的完整排查过程见[过程记录](history/latency-2026-11.md)。

## 当前结论（2026-11-08，0.5.0）

测试链路：Windows 11 原生发送端 → 有线局域网 → TrueNAS 上的原生接收端（PulseAudio、中断调度、实时优先级）→ USB 全速 DAC → 光纤 → 有源扬声器。

| 段 | 实测 | 方法 |
| --- | ---: | --- |
| Windows：应用提交 → VBAN 发出 | 2.7 / 5.4 ms（中位数 / P95，128 帧引擎、低延迟播放器） | `tools/latency/windows/sender-segment.ps1`，同一 QPC 时钟 |
| NAS：接收端客户端队列 + 输出 | 约 15–23 ms | 接收端状态中的 `latency_us`（客户端队列、PulseAudio 输出、ALSA 与 USB 在途数据） |
| 端到端：应用提交 → 扬声器 → 麦克风 | 稳态约 54–61 ms | `tools/latency/windows/acoustic.ps1`，麦克风采集包的 QPC 时间戳 |

两段软件合计约 20–28 ms，端到端其余约 30–35 ms 位于 DAC 之后：DAC 内部、光纤接收与扬声器内部处理，以及约 3 ms/m 的空气传播。这部分无法由软件调整。每次开始播放后的前约 15 秒，声学延迟会高约 15 ms，随后突然回落；同一时段接收端和 Windows 侧都没有对应变化，推测来自扬声器的光纤接收缓冲，尚未用对照测量确认。

**结论：软件链路已降到约 20–28 ms；在当前扬声器上，端到端 10–20 ms 的目标达不到。** 要进一步区分，需要在 DAC 之后接耳机或模拟输出做对照测量。

## 各环节的关键事实

- **Windows 引擎周期决定下限。** 10 ms 引擎下，“提交 → loopback 交付”恰好是两个周期，即 20 ms。改用 Microsoft 类驱动后，HDMI 为 128 帧（2.67 ms），Realtek USB 为 336 帧。发送端保持一个最小周期的静音流，让所有应用都按该周期混音。普通应用自身还保留约 20 ms 播放缓冲，这部分无法消除。
- **Voicemeeter 路径至少约 45 ms。** VAIO 端点的 loopback 位于其内部缓冲之后，实测滞后 61–104 ms。
- **接收端设置。** 2.67 ms 突发下，10/3 ms（`DESKTOP_NATIVE_LATENCY_MS` / `DESKTOP_NATIVE_JITTER_MS`）在 ±200 ppm 时钟偏差下通过 120 秒严格测试，P95 约 7.6–8.7 ms；目标 NAS 使用 10/3。
- **输出调度。** PulseAudio 默认的定时调度会让 ALSA 队列在 17–38 ms 间浮动；`OUTPUT_SCHEDULING=interrupt` 配合 2 ms × 3 片段，可固定在约 6 ms（含 USB 在途为 9–12 ms），需配合 `PULSE_REALTIME`。
- **时钟调节只看客户端队列。** 中断调度下 PulseAudio 报告的配置延迟为 0，若把设备延迟计入调节误差，会把队列抽空、每 2–3 秒欠载一次。
- **保持唤醒。** `DESKTOP_KEEP_AWAKE` 让 DAC 在电脑连接期间保持运行，避免唤醒耗时约 120 ms 和唤醒噪声。
- **设备停顿。** 输出停顿后，PulseAudio 拒绝写入但仍推进写位置，会导致此后连续写入失败；接收端现在会重新对齐。NAS 上 DAC 每约 63 秒停顿 60–100 ms 的根因是另一个循环重启的容器，删除后停顿消失（排查方法见[测量工具](../tools/latency/README.md)）。

## 测量注意事项

- 软件回环、null sink 监视器和接收端自身的延迟统计，都不能代替物理输出测量。
- WSL2 虚拟机时钟相对 Windows 漂移 1–3 %，还有约 20 ms 的跳变；Windows 发送到 WSL 接收的计时无效。本地测试接收端时，发送端须在同一容器内（`tests/native_vban.py`）。
- 声学测量依赖麦克风位置和房间噪声。比较不同配置时，应在同一位置、同一次会话中连续测量；每组至少 40 个标记，并区分会话开头和稳态。
