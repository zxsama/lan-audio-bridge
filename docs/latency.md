# 桌面音频延迟验证

本项目以有线局域网中的低延迟系统音频为优化方向。**当前未验证 Windows 到物理输出达到 10–20 ms**；最新声学端到端测量见下文“原生发送端与端到端”。 配置缓冲值、网络往返时间和软件监视器结果不能替代这一指标。

## 测量范围

2026-11-07 的 Windows 实测使用 Voicemeeter Standard 1.1.3.0、VAIO 3.4.1.9、48 kHz 双声道。发送端提交与本机 VBAN 标记接收采用同一 QPC 时钟。每组 8 个标记，相关系数均为 1.0，未检测到序号缺口；样本量较小，P95 等于该组最大值。

| Windows 发送路径 | 实际条件 | 中位数 | P95 |
| --- | --- | ---: | ---: |
| WinMM → Voicemeeter VBAN | VAIO 3072、引擎 512 帧 | 66.49 ms | 71.02 ms |
| WASAPI → Voicemeeter VBAN | 共享周期 128、分配 280 帧；VAIO 3072、引擎 512 帧 | 60.41 ms | 66.20 ms |
| WASAPI → Voicemeeter VBAN | 共享周期 128、分配 280 帧；原生 VAIO 1024、实际引擎 128 帧 | 45.04 ms | 48.84 ms |
| WASAPI endpoint loopback → 本机 UDP | 共享周期 128；capture 分配 1056 帧 | 70.84 ms | 78.43 ms |

这些结果不包括 LAN、NAS 和物理输出。低档测试结束后已恢复安装脚本管理的 3072/512 配置；1024/128 依赖特定客户端周期，尚未验证普通应用、系统登录和长期运行，因此未作为自动安装默认值。

驱动公布的最小共享周期为 128 帧，不能据此假设所有连接客户端的最大块长也是 128 帧。缩减 VAIO 内部缓冲必须同时满足发送端、引擎及连接客户端的需求，不能仅修改注册表后认定设置生效。参考 [Microsoft 低延迟音频](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/low-latency-audio)及 [Voicemeeter 手册](https://vb-audio.com/Voicemeeter/Voicemeeter_UserManual.pdf)。

## 接收端独立测试

原生接收器在本机 WSL Docker 的独立 PulseAudio null output 上接收真实 UDP PCM。软件观察时间从发送标记到 `output.monitor` 检出，包含测试程序的检测开销，**不包括真实音频设备缓冲或声学传播**。

| 请求配置：延迟 / 重排等待 | 连续测试 | 媒体期欠载 | 结果 |
| --- | ---: | ---: | --- |
| 8 / 4 ms | 60 秒 | 4 次 | 未通过稳定性门槛 |
| 12 / 6 ms | 120 秒 | 4 次 | 未通过；一次积压后 P95 达 26.43 ms |
| 16 / 8 ms | 120 秒、45,000 包 | 0 次 | 该次测试通过 |

上表是早期参数筛选，不代表最终实现的延迟。后续修正了时钟纠偏、实际队列目标和设备最低缓冲处理，并以最终实现重新测试。软件监视器可能早于设备完成播放，不能把观察值视为声卡延迟，也不能将它们与 Windows 分段结果相加后称为实测总延迟。

独立回归覆盖来源/格式校验、managed 握手、混音增益、HOLD 切换、空闲 cork/suspend、丢包及重排恢复。故障注入期间仍可能短暂欠载。

后续的 -200 ppm 发送偏差测试曾出现欠载。实际采样率核对表明调速已经生效，但测试输出时钟比单调时钟快约 396–398 ppm，叠加发送偏差后超出初版 ±500 ppm 纠偏范围。当前实现将范围调整到 ±2000 ppm、按实际时间积分、保留每秒 200 ppm 的平滑限速，并在每次变更后核对 PulseAudio ACK 和服务端采样率。

最终实现使用 `speex-float-5`、16/8 ms 请求和 2 ms monitor。队列控制目标是实际客户端 `tlength` 时长与 `configured_sink_usec` 之和，随着服务器协商值更新；初始填充也按实际客户端队列等待。

| 最终实现测试 | 持续时间 | 媒体期欠载 | 单路 P95 / 最大 | 冷启动 | 混音 P95 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 发送时钟 −200 ppm | 120 秒 | 0 | 15.54 / 16.26 ms | 8.66 ms | 8.41 ms |
| 发送时钟 +200 ppm | 120 秒 | 0 | 14.86 / 15.51 ms | 10.72 ms | 9.72 ms |
| 输出最低缓冲固定为 20 ms | 30 秒 | 0 | 41.14 / 41.72 ms | — | — |

前两组实际协商为客户端 10 ms、输出 6 ms，队列目标约 16 ms。第三组通过私有测试 shim 固定 null sink 的实际调度下限，并用 `pactl` 独立核对；服务器要求客户端 24 ms、输出 20 ms，总目标变为 44 ms，测试门槛明确放宽到 55 ms。它证明较高缓冲下的适配，不能作为低于 20 ms 的结果。

三组严格测试全部通过，最长近零段均只有正常正弦过零点的一个采样（0.0208 ms）。测试没有修改系统库或真实输出设备。该结果仍属于短时软件回环验证，尚不能代替长期运行及物理输出验收。

## 原生发送端与端到端（2026-11-07）

Windows 侧改用[原生发送端](windows-setup.md)后，同一 QPC 时钟测得“应用提交 → VBAN 发出”（每组 40 个标记）：

| 被采集端点 / 引擎周期 | 低延迟应用 中位数 / P95 | 普通应用（约 22 ms 自身队列） |
| --- | ---: | ---: |
| Voicemeeter VAIO 路径（对照） | 45.0 / 48.8 ms | 60–66 ms |
| 厂商驱动，480 帧 | 20.0 / 20.1 ms | 30.0 ms |
| Realtek，系统 USB Audio 2.0 驱动，336 帧 | 7.1 / 14.2 ms | 21.0 / 28.0 ms |
| HDMI，系统 HD Audio 驱动，128 帧 | 2.7 / 5.4 ms | 21.4 ms |

10 ms 引擎下的 20 ms 下限正好是两个周期：一个周期等待引擎拉取，一个周期等待 loopback 交付。该下限只能通过更小的引擎周期降低。

接收端在同一容器时钟域内用 `--burst-ms` 模拟 loopback 的整周期交付：16/8 ms 在 10 ms 和 2.67 ms 突发下 30 秒均无欠载（P95 12.6 / 15.3 ms）；12/6、10/5、8/4 ms 在 10 ms 突发下欠载。Windows 发送到 WSL 接收不能用于计时：WSL2 虚拟机时钟相对 Windows 漂移 1–3 %，并出现约 20 ms 跳变，会表现为接收队列持续增长后溢出和欠载。

声学端到端（Windows 标记 → 原生发送端 → NAS 0.4.0 原生接收 16/8 ms → USB DAC → 扬声器 → Logitech BRIO 麦克风，按麦克风采集包的 QPC 设备时间戳计时）：中位数 92 ms，28/30 个标记检出，个别 107–139 ms。播放期间 NAS 的 ALSA 队列为 17–38 ms（PulseAudio 定时调度，2 s 硬件缓冲、自适应水位）。剩余部分包括接收端队列、DAC、扬声器内部处理和约 3 ms/m 的声学路径，目前尚未逐项分离。为此新增 `OUTPUT_SCHEDULING=interrupt`（固定小周期 ALSA 队列）和 `PULSE_REALTIME`，已在目标 NAS 验证：Pulse I/O 线程为 SCHED_RR、接收器为 SCHED_FIFO，ALSA 实际为 96 帧 × 3（6 ms），播放时 ALSA 延迟 9–12 ms（含 USB 在途数据），未见 xrun 或 UDP 丢包。同一声学方法测得稳态 52–64 ms（中位数 58 ms），较 92 ms 下降约 34 ms。一次 80 标记测试中出现过约 5 秒的 137–249 ms 异常和 10 个未检出标记，复测未重现，原因未确定。每次会话开始时 DAC 从挂起恢复约 120 ms，期间积压的音频使前约 15 秒多出约 20 ms；为此新增 `OUTPUT_IDLE_SUSPEND_MS`；部署后，DAC 保持唤醒的 8 秒间隔后会话起点从约 81 ms 降到约 68 ms，剩余的起点超额来自接收端起播等待（`DESKTOP_NATIVE_JITTER_MS`）在稳态目标之外的积压。接收端在 2.67 ms 突发下 10/3 ms 通过 120 秒严格测试（P95 约 8.7 ms），比 16/8 ms 少约 7 ms。目标 NAS 上 10/3 ms 稳态约 49 ms；状态镜像显示播放期间每 2–3 秒一次欠载、调速持续 +1100 至 +1500 ppm：中断调度下 Pulse 报告 `configured_sink_usec = 0`，控制器把 6–12 ms 的设备延迟当成多余积压。修正后只调节接收端环形缓冲与服务器客户端队列，本机 ±200 ppm 120 秒严格测试 P95 为 7.6 / 7.8 ms。`DESKTOP_KEEP_AWAKE` 部署后 DAC 在电脑连接期间保持 RUNNING。

目标 NAS 上 USB DAC 约每 62–63 秒停顿一次，每次 60–100 ms（少播约 50 ms），空闲和播放时都会发生，会造成断音，光纤输入的扬声器可能因信号中断而发出轻微噪音。多核同时计时显示只有 CPU0 被占用（其余核无停顿，不是 SMI），期间 CPU0 时间几乎全部在 HI 软中断（USB 传输完成处理），而 DAC 所在 xHCI 控制器的中断（IRQ 388）也由 CPU0 处理。停顿中 PulseAudio 拒绝写入时仍推进写入位置，导致此后连续写入失败（一次 1052 次）；接收端现在在服务器溢出后像欠载一样重新对齐写入位置。把该中断改由其他核处理是否能消除停顿，尚待在目标 NAS 上验证。剩余约 25 ms 尚未分离，可能来自扬声器内部处理、声学路径或麦克风时间戳。

## 目标主机验收

应分别记录首声、持续播放的中位数/P95/最大值，以及欠载、丢包、延迟积压。至少覆盖正常系统应用、隐藏运行、电脑与手机并播、两路独立停止、接收器故障恢复和长时间播放。输出设备从 suspend 唤醒的首声需单列。

测量应使用低幅度已知标记，采用同钟录制或校准的硬件回环。公共日志仅记录计数与时序，不保存实际用户音频。`SUSPENDED` 表示软件释放了输出；外部设备是否完全停止数字载波，需要物理验证。
